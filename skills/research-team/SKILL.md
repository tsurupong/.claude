# 調査チーム

メインの文脈に生データを入れないことが編成の根拠(コンテキスト汚染の防止)。
メインセッションは問いの分割・割当・統合・裏取りだけを行う。

## チーム編成

| 担当 | model | 呼ぶ条件 |
|---|---|---|
| research-explorer | haiku | 大量ファイル・ログの読み込み(単一1000行超 or 累積3000行超) |
| Explore(組み込み) | - | コードの所在・構造の探索(どこに何があるか) |
| bug-investigator | sonnet | バグ・障害・想定外挙動の原因調査 |
| rootcause-auditor | opus | 原因判定の独立検証。高リスク対応(削除・障害対応)の前に必須 |

## 手順

1. **問いの分解**: 調査を「独立に答えられる問い」に分割し、各問いに
   期待する成果物形式(表/一覧/判定/要約)を1文で書く。
2. **割当**: 上の表の条件で担当を決める。小さな1点確認(ファイル1つ・既知の場所)は
   委譲せず自分で読む方が速い。
3. **並列起動**: 独立な問いは1メッセージで一斉に投げる(workflow-patterns P1)。
   各指示に「対象範囲・返す形式・read-only であること」を明記。
4. **統合と裏取り**: 結論間の矛盾チェックは自分で行う。高リスク結論
   (削除対象・障害原因・互換性)は rootcause-auditor または独立2手段で裏取り(P5)。
   担当の報告を無検証で採用しない(重要な数字は再計測)。
5. **報告**: 結論先頭。全主張に根拠(パス/行/実測値)。確度の低い箇所は「未確認」と明記。

## 常駐往復モード(SendMessage)

中間報告を見てから次の問いが決まる対話的な調査では、workflow-patterns P9 に従い
担当を name 付きで維持する:

- **追い問い**: SendMessage で同じ担当に送る(毎回新規起動すると対象の読み込みを
  やり直すため、文脈維持の方が速く一貫する)
- **障害対応**: 担当が権限拒否・ツール不在を報告してきたら、許可済みツールだけで
  成立する代替手順を具体的に返す(例: bash 不可なら Grep/Glob/Read の呼び出し形を示す)。
  親による代行・迂回はしない
- **解散条件**: 問いが尽きた時。アイドル通知だけで報告本文が来ない場合は
  SendMessage で報告送信を要求してから解散する

## 掟

- 調査「だけ」を頼まれた時は分析を返して止まる。修正・削除はしない
  (対応まで必要なら fix-team に引き継ぐ)。
- 環境は変更しない(read-only)。書き込みが必要になったら理由を添えてユーザーに戻す。
- 調査が2往復しても収束しない時は、問いの分割単位を疑って組み直す。
