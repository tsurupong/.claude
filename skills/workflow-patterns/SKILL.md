# 作業パターン集

## P1: 調査の並列ファンアウト
独立した調査は1メッセージで並列に投げる(逐次にしない)。各エージェントには
「対象範囲・返す形式・読み取り専用」を明記。結果の統合は自分でやる。

## P2: 重い読み込みの隔離
1000行超のファイル群・大量ログはサブエージェント(research-explorer, read-only)に読ませ、
結論だけ受け取る。メイン文脈には生データを入れない。

## P3: 計画→承認→実行→検証(標準ループ)
Plan Modeまたは計画提示→ユーザー承認→小さく実装→都度検証→完了報告(証拠付き)。
承認済み計画は「許可範囲の契約書」として扱い、逸脱時は再承認。

## P4: チェックポイント方式(長時間)
フェーズ毎に「ここまでの確定事項」を書き出す。中断・コンテキスト圧縮・
モデル切替が起きても、その書き出しから再開できる状態を常に保つ。

## P5: 裏取りの二重化
高リスクな結論(削除対象の特定・障害原因・互換性判断)は、独立した2手段で
確認一致してから行動(例: diffとsha256、ログとコード実読)。

## P6: 誤り訂正の作法
自分の過去の発言と矛盾する事実が出たら、①訂正を明示 ②原因を一言
③影響範囲の更新、の順で最優先報告(次の成果物の冒頭で)。

## P7: ブロック時の迂回
ツールや権限にブロックされたら: ①より小さく分割して再試行 ②趣旨を保った代替手段
③それでも駄目なら「何をしようとして・なぜ必要か」を報告しユーザーに委ねる。
ブロックの趣旨を回避する裏口は使わない。

## P8: レビュー反復サイクル(/loop 運用)
「レビュー→指摘リスト→修正→再レビュー」を /loop で回す時の型:
①レビューは review-orchestrator(コード)/ doc-reviewer(設計書)に委譲
②指摘は blocking / advisory に区分し、blocking ゼロを終了条件にする
③各周回の冒頭に「前回からの差分と残指摘数」を1行で記録(収束の可視化)
④3周して残指摘数が減らない場合は停止し、指摘の妥当性自体を review-auditor で検査。

## P9: 常駐チーム運用(SendMessage)
メンバーとの往復対話が必要な時だけ使う(使い切り委譲で足りるなら使わない)。
- **起動**: Agent 呼び出しに name を付ける。以後 SendMessage({to: name}) で
  文脈を保ったまま追加指示・追い問いができる(毎回新規起動すると読み込みをやり直す)。
- **回収**: 成果物はファイル保存ではなく最終メッセージで受け取る(サブエージェントの
  レポートファイル書き込みはハーネスが拒否する)。アイドル通知だけ来て報告本文が
  届かない場合は、SendMessage で報告送信を要求する。
- **権限**: メンバーが権限拒否に当たっても、親が代行したり迂回させたりしない。
  許可済みツールだけで可能な代替手順を返すか、ユーザーに戻す。
- **解散**: 開始前に解散条件を決める(blocking ゼロ / 問いが尽きた / 往復3回)。
  条件を満たしたら結果を統合して終了。無限往復はしない。
