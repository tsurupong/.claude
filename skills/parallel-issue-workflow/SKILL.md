# 並列 issue 開発(worktree 運用)

1 issue = 1 worktree = 1 セッションで並列実行し、最後にまとめて回収する。

## 起動: タスク定義テンプレート(型A)

```
# Task <番号>-<issue名>
## Title      — 日本語の機能タイトル
## Requirement — 要件
## 背景        — 設計書/ADR への参照
## 要求        — 具体的な修正指示・既存との差分
## 完了条件    — 検証仕様(新規テストに assert を書けるレベルで具体化)、
                差分ファイル一覧、既存テストの変更禁止、build/test/lint 全通過
## 制約        — 差分範囲の上限(対象ファイルを明示)、既存プロトコル不変の宣言
```

完了条件の具体度が完走率を決める(エージェントが自力でテスト設計できる水準に書く)。

## 投入時のルール
- **依存があるタスクは並列投入しない**。やむを得ず投入する場合は
  「<前提物>が存在しない場合はこのタスクを進めず失敗として終了する」という
  前提ゲートを必ずタスク文面に書く(依存欠落時の即時 fail が機能した実績あり)。
- 権限は実装/検証を分離する(worktree 側では install/test/commit をブロックし、
  検証・コミットは回収後に親側でまとめて行う)。
- コミット・push は承認制のまま。worktree 側で完結させない。

## 回収: 集約表
全 worktree を以下の表に集約してから統合判断に入る:

| issue | 実装 | テスト | コミット | 状態 |
|---|---|---|---|---|
| (例) 30-scheduler-lib | ○ | 27/27 PASS | 未 | 承認待ち |

- 状態は「PR済 / 検証済 / 実装のみ / 依存fail / 途中」の5区分。
- 「実装○・検証✗(権限ブロック)」は失敗ではなく**承認待ち**。
  まとめて検証→コミットのフェーズへ送る。
- 同一 worktree に複数セッション(リトライ・再開)がある場合は最新だけでなく全て確認。

実績(2026-07, 13並列): 完走2・承認待ち相当7・依存fail 1・途中3。
ボトルネックは回収・集約の未定型化だったため、回収表の作成までを本スキルの完了条件とする。
