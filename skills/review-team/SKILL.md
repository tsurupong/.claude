# レビューチーム

メインセッションは自分でレビューせず、対象の判定と結果の受け渡しに徹する。
「作る者と検証する者を分ける」が編成の根拠(ai-team-design 準拠)。

## チーム編成

| 担当 | model | 役割 |
|---|---|---|
| review-orchestrator | opus | 司令塔。観点判定→担当を並列起動→auditor 検査→統合 |
| code-reviewer | sonnet | 汎用コード品質(重大度順) |
| security-reviewer | sonnet | 脆弱性+攻撃シナリオ+修正案 |
| doc-reviewer | sonnet | 設計書・企画書の整合性(blocking/advisory 区分) |
| review-auditor | opus | 指摘の妥当性検査(実コード照合)。担当を直接呼んだ時の blocking 指摘に必須 |

## 手順

1. **対象の確定**: コード差分か文書か。範囲(コミット/ファイル一覧)と観点を宣言してから起動。
   差分レビューは git diff の取得可否を先に確認する。
2. **起動の分岐**:
   - コード差分(3ファイル以上 or 認証・入力処理・外部通信を含む)→ review-orchestrator に一括委譲
   - 軽微な差分(〜2ファイル・ロジック小)→ code-reviewer 単体
   - 設計書・企画書 → doc-reviewer(文章表現の推敲だけなら doc-editor)
3. **検査**: orchestrator を通さず担当を直接呼んだ場合、blocking 指摘は review-auditor の
   妥当性検査(実コードで再現するか)を通してから採用する。
4. **統合報告**: 重大度順。各指摘に file:line と根拠。**修正はしない**
   (修正まで頼まれたら fix-team に引き継ぐ)。
5. **反復レビュー**(/loop 運用)は workflow-patterns P8 準拠
   (blocking ゼロを終了条件、3周収束しなければ停止)。

## 常駐往復モード(SendMessage)

一括委譲で完結しない時のみ、workflow-patterns P9 に従い担当を name 付きで起動する:

- **指摘の深掘り**: 根拠が薄い指摘には SendMessage で「実コードでの再現根拠」を追加要求
- **修正後の再検査**: 同じ担当に SendMessage で修正差分を再送し、文脈を保ったまま
  再レビューさせる(新規起動より速く、指摘の一貫性が保たれる)
- **解散条件**: blocking ゼロ、または報告受領後に追加質問が尽きた時。
  修正との自動往復が必要なら fix-team の常駐往復モードに引き継ぐ

## 掟

- 独立した観点(コード品質/セキュリティ/文書整合)は1メッセージで並列起動。
- レビュー対象を書いた本人(impl-builder 等)には検証させない。
- 指摘ゼロでも「見た範囲と見ていない範囲」を明記して報告する。
