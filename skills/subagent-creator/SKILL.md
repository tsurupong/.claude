# Subagent Creator

Claude Code のカスタムサブエージェント定義ファイルを作成・改修するための実務手順。
定義ファイルは「YAML フロントマター(設定) + Markdown 本文(システムプロンプト)」の Markdown ファイル。

参照資料:
- フロントマター全フィールドの仕様 → `references/frontmatter.md`(フィールドを設定する前に該当箇所を読む)
- 編成・モデル割当・新設判断の指針 → `ai-team-design` スキル

## 手順

### 1. 作る前に確認する3点

1. **本当にサブエージェントか**。メイン会話で使う再利用プロンプトなら Skill、
   会話をまたぐ常時ルールなら CLAUDE.md/rules が適切。サブエージェントが向くのは
   「大量に読む・出力するが、結論だけ戻ればよい」自己完結タスク。
2. **既存と重複しないか**。`~/.claude/agents/` と `.claude/agents/` を一覧し、
   同名・同役割がないか確認する。同名は高優先度側しか読み込まれない。
3. **スコープ**。個人の全プロジェクト用 → `~/.claude/agents/`。
   プロジェクト固有・チーム共有(バージョン管理に入れる)→ `.claude/agents/`。

### 2. 設計を決める(フロントマター)

必須は `name` と `description` のみ。他は必要な時だけ書く。

- **name**: 小文字ハイフン区切りで一意。ファイル名と一致させると管理しやすい。
- **description**: 委譲判断に使われる最重要フィールド。
  「何をする担当か」+「いつ使うか」を必ず両方書く。積極的に使わせたいなら
  「実装完了後・コミット前に使用」のようにトリガー条件を具体的に書く
  (英語なら "use proactively" が定番)。
- **tools**: 役割の最小権限にする。調査系は `Read, Grep, Glob` + 必要な読み取り Bash のみ。
  `Bash(git diff *)` のようにコマンド単位で絞れる。省略すると全ツール継承。
  逆に「ほぼ全部でこれだけ禁止」なら `disallowedTools` を使う(両方指定時は
  disallowedTools が先に適用)。
- **model**: 省略時は親セッション継承(`inherit`)。定型・大量処理は `haiku`、
  実装・レビューは `sonnet`、計画・アーキ判断は `opus`(ai-team-design 参照)。
- その他(`permissionMode` / `hooks` / `skills` / `memory` / `mcpServers` /
  `maxTurns` / `isolation` / `effort` / `background` / `color`)は
  `references/frontmatter.md` を読んでから設定する。安易に
  `permissionMode: bypassPermissions` を書かない。`memory` は同種タスクの学びを
  蓄積させたい定常運用の担当にのみ有効化する(単発・使い捨てには付けない)。

### 3. 本文(システムプロンプト)を書く

本文がサブエージェントのシステムプロンプトそのものになる。完全な Claude Code の
システムプロンプトは渡らず、CLAUDE.md は読み込まれる(組み込み Explore/Plan を除く)。

書く内容(code-reviewer.md 等の既存定義が実例):
1. **役割宣言 + やらないこと**を1〜2文で。「レビュー専任。自分では修正しない」のように
   境界を明示すると逸脱しない。
2. **手順**を番号付きで。呼び出された直後に何をするかから書く。
3. **出力形式**を固定する。1エージェント=1つの成果物形式(表/判定/差分/計画書)。
   親会話に戻るのは最終テキストだけなので、「結論を先頭に、根拠に file:line を付ける」
   のような返し方の指定が効く。
4. **言語指定**。このユーザー環境では「出力は日本語」を明記する。

### 4. 配置して動作確認する

1. ファイルを配置する。既存の agents ディレクトリなら数秒で自動検出され再起動不要。
   ディレクトリ自体を新規作成した場合のみ再起動が必要。
2. 検証: フロントマターが YAML として妥当か(`name`/`description` があるか、
   tools のツール名に誤字がないか — 全エントリが解決不能だと起動を拒否される)。
3. 呼び出しテスト: 「Use the <name> subagent to …」または `@agent-<name>` で
   明示呼び出しし、期待した形式の結果が返ることを見る。
4. 完了報告には配置パスと動作確認の結果を添える(「書けた」でなく「動くのを見た」)。

## テンプレート

```markdown
---
name: log-analyzer
description: ログファイルの大量読み込みと異常抽出の担当。障害調査でログを調べる時、エラーの発生パターンを集計する時に使用。
tools: Read, Grep, Glob, Bash(wc *), Bash(head *), Bash(tail *)
model: haiku
---

あなたはログ解析専任。修正や設定変更はしない(発見の報告のみ)。

手順:
1. 対象ログの範囲(ファイル・期間)を特定する。
2. エラー・警告を種類別に集計する。
3. 時系列で最初の異常発生点を特定する。

出力形式(日本語):
- 結論(1〜2文)
- 異常の一覧表: 種類 / 件数 / 初出時刻 / 代表例(file:line)
- 追加調査が必要な点
```

## よくある失敗

- **description が「何をするか」だけ**: いつ使うかがないと委譲されない。
- **tools を省略して全権継承**: 調査系が Write/Edit を持つと事故のもと。役割の最小に絞る。
- **本文が役割宣言だけ**: 手順と出力形式がないと毎回違う形で返ってくる。
- **1エージェントに複数の役割**: 「調査して修正もする」は分ける(検証者と作成者は別)。
- **plugins 由来の定義に hooks/mcpServers/permissionMode を書く**: プラグイン配布では
  無視される。必要なら .claude/agents/ にコピーする。
