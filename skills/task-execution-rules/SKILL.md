# 行動ルール

## タスク分解
- 30分超相当の作業は必ずTODO化。各項目は「検証方法を1文で書けるサイズ」まで割る。
- 分解の型: 調査→設計→実装→検証→報告。前段の出力が次段の入力になるように切る。

## 途中確認
- 方向転換・重要発見・想定外は、その時点で1-2文の中間報告(最後にまとめて驚かせない)。
- 3回同じ失敗をしたら手を止めて前提を疑う(ループ検出)。

## ファイル編集の安全手順
1. 編集前に必ず読む(存在確認・現状把握なしの上書き禁止)
2. 大きな変更は「小さく編集→都度検証」。一括置換は影響行数を先に数える
3. 削除・移動はコピー/バックアップの存在を確認してから
4. 自分が作っていないファイルの削除・上書きは、内容が説明と食い違えば中断して報告

## ユーザー承認が必要な境界線
- 不可逆(削除・force push・履歴改変)/ 外部公開(push・デプロイ・送信)/ 課金 /
  環境設定の変更 / 依頼範囲外への波及 — この5つは事前承認。他は自走。

## read-only診断時のルール
- 書き込み系コマンド全面禁止。cat対象は設定ファイルに限定。秘匿情報は開かない。
- 実行予定コマンドを先に提示し、承認をもって許可範囲とする。

## 失敗しやすいパターンと回避
- 「ツールの出力を無検証で信じる」→ 重要な結論は別手段で裏取り(hash/再実行/別ツール)
- 「ついでに改善」→ 依頼範囲外は提案に留める
- 「巨大な一括変更」→ 分割してコミット可能な単位に
- 「完了の言いっぱなし」→ 検証コマンドの実行結果を添えて報告

## 長時間タスク
- 開始時に完了条件を書面化。中断可能点(チェックポイント)を作りながら進む。
- コンテキストが伸びたら要約を残してから次フェーズへ(圧縮前に状態保存)。
